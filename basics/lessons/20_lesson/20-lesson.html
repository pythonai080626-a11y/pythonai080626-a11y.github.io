When It Breaks — try, except, finally 🛟

Until today a red traceback meant the program was over. Today it stops meaning that. An error is an object Python throws, it travels back up through every function that was waiting, and if nobody catches it the program dies. So we catch it: try holds the risky line, except is the net under it, else runs only when nothing broke, and finally runs whatever happens. And with raise you get to be the one who throws.

01_errors.py

The Red Wall of Text 💥

You have seen this all year. You typed abc where a number was wanted, the program stopped, and the screen went red.

x = int(input('Enter a number? ')) print(x)
Enter a number? abc Traceback (most recent call last): File "01_errors.py", line 2, in <module> x = int(input('Enter a number? ')) ValueError: invalid literal for int() with base 10: 'abc'

Read the last line first. It has two halves, and both matter:

HalfWhat it is
ValueErrorthe type of the error — its family name. This is what you will catch by name in a minute.
invalid literal for int()…the message — the sentence explaining what went wrong this particular time.
An error is not a printout. It is an object that Python builds and throws, and the red text is only what gets printed when nobody catches it. Everything today is about catching it before it reaches the screen.
The families you already meet
ErrorWhat you did
ValueErrorint('abc') — the right type, a value it cannot use
ZeroDivisionError10 / 0
TypeError'no answer' ** 3 — the wrong type entirely
KeyError{'a': 1}['b'] — a key that is not there
IndexError[1, 2][9] — past the end of the list
NameErrorusing a variable you never made
The full list, with an example of each, is on today's topic page: Try / Except.
01_errors.py

It Climbs Back Up Through Every Call 🪜

Four functions. a calls b, b calls c, c calls d, and only d does anything wrong.

def d(a, b): print(a / b) def c(): print('c') d(1, 0) def b(): print('b') print('c') c() def a(): b() a()
b c c Traceback (most recent call last): File "01_errors.py", line 41, in <module> a() File "01_errors.py", line 39, in a b() File "01_errors.py", line 36, in b c() File "01_errors.py", line 31, in c d(1, 0) File "01_errors.py", line 27, in d print (a/b) ZeroDivisionError: division by zero

That is not five errors. It is one error and the road it travelled. Nobody in d caught it, so it was handed back to c; nobody there caught it either, so back to b, to a, and out of the program.

Read a traceback bottom to top: the last line is what broke, the lines above are who asked for it.
This is the good news hiding in the bad news. Because the error travels upwards, you do not have to catch it where it happened — you can catch it anywhere along that road. Which is the whole question of the last topic today.
01_errors.py

Two Ways an Error Starts 🎯

So far Python has always been the one deciding. There is a second way, and it is a single word:

1 · Python decides
vs
2 · you decide — raise
raise ZeroDivisionError("it was me!") raise IndexError("ha ha ha")
ZeroDivisionError: it was me!

Same red text, same behaviour — the only difference is who threw it. The string in the brackets becomes the message, so write one a human can act on.

Where you will actually use it

A function that has not been written yet, but that you want to call from your story already — exactly the story-first habit from last lesson:

def predict_stock_price(stock_name): raise NotImplementedError("not implemented yet") print(predict_stock_price('Microsoft'))
NotImplementedError: not implemented yet
Compare that to pass. A stub with pass quietly hands back None and the bug shows up three functions later. A stub that raises says so loudly, on the spot, in a way you cannot walk past.
Refuse work you cannot do. When a function is handed something it has no honest answer for, raising is better than inventing one:
def my_div(a, b): if b == 0: raise ZeroDivisionError("b is zero - cannot divide by it") return a / b
That is tonight's first homework task, and the rest of this lesson is about who catches it.
02_errors.py

try / except — the Net Under the Line 🛟

Put the risky code inside try. Put what to do about it inside except. If nothing goes wrong the except block never runs at all.

try: number = int(input("Enter a number: ")) print(f"You entered: {number}") except: # if error: print('--- Error occurred ---') print('Goodbye')
they type 12
Enter a number: 12 You entered: 12 Goodbye
they type abc
Enter a number: abc --- Error occurred --- Goodbye

Look at the second column. There is no red, no traceback — and Goodbye still printed. That last part is the whole point: the program did not die, it carried on to the next line.

Either the try block finishes, or the except block does. Then the program carries on regardless.
A bare except: is a beginner's tool, and today is the last day you use it. It swallows everything — including the typo in your own code — and tells you nothing about what went wrong. The next topic fixes that.
02_errors.py

Catch It By Name, and Hold It 🏷️

One try can have several except blocks. Python runs the first one that matches the error's type, and ignores the rest. And as e hands you the error object itself, so you can print its message.

try: number1 = int(input("Enter a number: ")) number2 = int(input("Enter a number: ")) div1 = number1 / number2 except ValueError as e: # if ValueError: print(f"The value you entered is not a number! \n{e}") except ZeroDivisionError as e: print(f"You divided by Zero! \n{e}") except Exception as e: # if all other errors: print(f"Some error ... not sure ...") print('Goodbye')
They typeWhich block runsWhat e holds
12 then 4none of them—
abcexcept ValueErrorinvalid literal for int() with base 10: 'abc'
12 then 0except ZeroDivisionErrordivision by zero
anything else oddexcept Exceptionwhatever it was
as e is just a variable name — e is the error object. print(e) gives you Python's own message, which is nearly always more useful than a sentence you invented.
Making it red on purpose 🎨

Those \033[91m and \033[0m in the lesson file are not python — they are codes the terminal understands. One switches the colour on, the other switches it back off.

print(f"\033[91mYou divided by Zero! \n{e} \033[0m")
You divided by Zero! division by zero
Always switch the colour back off with \033[0m. Forget it and everything printed afterwards stays red, including the parts that went fine.
02_errors.py

Narrow First, Wide Last ⚠️

Exception is the family that almost every error belongs to. ValueError is an Exception. ZeroDivisionError is an Exception. So an except Exception block will happily catch them too — and because Python takes the first block that matches, putting it at the top means nothing below it ever runs.

wrong — wide first
try: 1 / 0 except Exception: print('something broke') except ZeroDivisionError: print('divided by zero')
something broke
right — narrow first
try: 1 / 0 except ZeroDivisionError: print('divided by zero') except Exception: print('something broke')
divided by zero

The left-hand version is not an error — Python runs it happily. It is just useless: the specific block underneath is dead code that can never run.

Catch the small boxes first. Keep Exception for last, as the net that catches whatever you did not think of.
Keeping a last except Exception as e is good practice — but print e inside it. An "oops, something went wrong" that hides the message is how a bug survives for a week.
05_errors.py

Two Errors, One Block 🎣

When two different errors deserve exactly the same response, you do not need two blocks. Put them in brackets, separated by a comma — a tuple, from last lesson.

the long way
try: data = int(input("Enter: ")) except ValueError as e: print(f"Input error: {e}") except TypeError as e: print(f"Input error: {e}")
the shortcut
try: data = int(input("Enter: ")) except (ValueError, TypeError) as e: print(f"Input error: {e}")
Enter: hello Input error: invalid literal for int() with base 10: 'hello'
The brackets are not optional. except ValueError, TypeError: without them is a SyntaxError in modern Python. It is one tuple, so it needs its brackets.
Only group errors that genuinely deserve the same handling. Two errors sharing a block because you could not be bothered to write the second one is how you end up printing "input error" at somebody whose file was missing.
04_errors.py

else — Only If Nothing Broke ✅

A third clause, and it does the opposite of except: it runs only when the try block finished without a single error.

try: number1 = int(input("Enter a number: ")) number2 = int(input("Enter a number: ")) div1 = number1 / number2 except ValueError as e: print(f"not a number! {e}") except ZeroDivisionError as e: print(f"divided by zero! {e}") else: print('div successfully ', div1)
Enter a number: 10 Enter a number: 4 div successfully 2.5

You could have written that print as the last line inside try and it would behave the same. else is better for one reason: keep the try block as short as you can. Only the lines that might actually break belong in there. Anything in the try block is a line whose errors you are silently agreeing to catch — including ones you never meant to.

try: risky + the celebration
→
try: risky only else: the celebration
else is optional and you will not use it every day. When you do, it is because you want a clean line between "the thing that might fail" and "what to do when it did not".
04_errors.py

finally — Runs No Matter What 🧹

The fourth clause, and the stubborn one. finally runs when it worked. It runs when it broke. It runs when the error was caught, and it runs when it was not.

try: number1 = int(input("Enter a number: ")) number2 = int(input("Enter a number: ")) div1 = number1 / number2 except ValueError as e: print(f"The value you entered is not a number! {e}") finally: print('***** FINALLY BLOCK -- close file / connections *****') print('Goodbye')
What happensWhich blocks run, in order
no error at alltry → else → finally
an error you caughttry → except → finally
an error you did not catchtry → finally → then the program still crashes
a return inside trytry → finally → only then does the value go back

That third row is the one worth staring at. The second half of the lesson file has a try with no except at all — just finally:

try: number1 = int(input("Enter a number: ")) number2 = int(input("Enter a number: ")) div1 = number1 / number2 finally: print('***** FINALLY BLOCK *****')
Enter a number: 5 Enter a number: 0 ***** FINALLY BLOCK ***** Traceback (most recent call last): ... ZeroDivisionError: division by zero

The cleanup happened, then the program crashed anyway. That is not a bug — that is the entire promise of finally. It is not there to handle the error; it is there to make sure the tidying up happens on the way out.

There is no way out of a try block that skips finally.
What actually goes in there: closing a file, closing a database connection, letting go of a lock, switching the terminal colour back. Things that would leave a mess behind if the program fell over mid-way.
03_errors.py

Where Should You Catch It? 🎯

The error climbs back up through every call, so you get to choose the floor you catch it on. Here is the same function catching its own error — and quietly ruining the program that called it.

def my_div(a, b): try: return a / b except ZeroDivisionError as e: return "no answer" # why is this bad? a = int(input("Enter a number: ")) b = int(input("Enter a number: ")) x = my_div(a, b) print(x ** 3)
Enter a number: 10 Enter a number: 0 TypeError: unsupported operand type(s) for ** or pow(): 'str' and 'int'
Look what it did. The function swallowed a perfectly clear ZeroDivisionError and handed back the string "no answer". Four lines later the program blew up on x ** 3 with a TypeError that has nothing to do with the real problem. The error got hidden, moved, and disguised.

The function's job is to divide. It does not know whether the caller wants to print a message, ask again, or give up — so it should not decide. Let the error travel, and catch it where somebody actually knows what to do:

catching too deep
def my_div(a, b): try: return a / b except ZeroDivisionError: return "no answer" x = my_div(a, b) print(x ** 3)
TypeError: ... 'str' and 'int'
catching where it means something
def my_div(a, b): return a / b try: x = my_div(a, b) print(x ** 3) except ZeroDivisionError: print('no answer')
no answer
The rule of thumb: catch an error at the level that can actually do something about it. Deep inside a helper function you usually cannot — so let it travel. Up in the main story, where you can ask the user again or print a sensible message, you can.
And never, ever return a string like "no answer" where a number was promised. Whoever calls that function is going to do maths on it.

Homework

Homework — Three Crashes to Catch ✍️

Three lines that break, three different errors. Your job each time is the same: let it break first, read the red text, and only then wrap it in try / except so the program survives.

Rules for all three:
  1. Run it without the try first. You cannot catch an error by name until you have seen its name.
  2. Never a bare except: — catch KeyError, TypeError, ValueError by name.
  3. Print something a human can read. After the except, print 'Goodbye' so you can prove the program did not die.
1 · A key that is not in the dictionary 🔑

Print a dictionary on screen, ask the user for a key, and print the value that goes with it.

Use the square brackets — prices[key]. Do NOT use .get(). The whole point is that square brackets crash when the key is missing, and that is the crash you are going to catch. In the except, print <key> not exist.

prices = {'apple': 12, 'banana': 7, 'cherry': 25} print(prices) key = input("Which fruit? ") # try: print prices[key] <-- square brackets, not .get() # except KeyError: print(key, 'not exist')
a key that is there
{'apple': 12, 'banana': 7, 'cherry': 25} Which fruit? banana 7 Goodbye
a key that is not
{'apple': 12, 'banana': 7, 'cherry': 25} Which fruit? mango mango not exist Goodbye
A trap in this one. KeyError is the one error whose message keeps its quotes:
except KeyError as e: print(e) # prints 'mango' - with the quotes!
So build the sentence from your own key variable, not from e, or you will print 'mango' not exist.
2 · Changing a tuple 🔒

Take a tuple, and try to change the item at index 0 to 99. It will not work — that is exactly what lesson 19 was about. Catch the error instead of letting it kill the program, and print the tuple afterwards to prove it never changed.

t = (1, 2, 3) # try: t[0] = 99 # except TypeError as e: print a message and print(e) print(t)
cannot change a tuple: 'tuple' object does not support item assignment (1, 2, 3) Goodbye
The error you are catching here is a TypeError, not a ValueError. Run it once without the try and the red text tells you which — that is the habit.
3 · Removing something that is not in the list 🍊

Here is the line. It raises a ValueError, because you cannot remove what was never there:

fruits = ["apple", "banana"] fruits.remove("orange") # ValueError: list.remove(x): x not in list

Wrap it in try / except ValueError, print a message that says which fruit was missing, and print the list afterwards.

fruits = ["apple", "banana"] # try: fruits.remove("orange") # except ValueError as e: say orange is not in the list, print(e) print(fruits)
orange is not in the list: list.remove(x): x not in list ['apple', 'banana'] Goodbye
Then make it not crash in the first place. Add the if "orange" in fruits: version underneath, as a comment or a second block. try / except is for what you could not have checked; a plain in test is better when you could.

שיעורי בית — שלוש שגיאות לתפוס ✍️

שלוש שורות שנשברות, שלוש שגיאות שונות. המשימה בכל אחת מהן זהה: קודם תנו לזה להישבר, תקראו את הטקסט האדום, ורק אז תעטפו ב-try / except כדי שהתוכנית תשרוד.

כללים לשלוש המשימות:
  1. קודם הריצו בלי ה-try. אי אפשר לתפוס שגיאה בשם שלה לפני שראיתם מה השם.
  2. אף פעם לא except: ריק — תפסו KeyError, TypeError, ValueError בשם.
  3. הדפיסו משהו שבן אדם יכול להבין. אחרי ה-except הדפיסו 'Goodbye', כדי להוכיח שהתוכנית לא מתה.
1 · מפתח שלא נמצא במילון 🔑

הדפיסו מילון על המסך, בקשו מהמשתמש מפתח, והדפיסו את הערך ששייך לו.

השתמשו בסוגריים המרובעים — prices[key]. אל תשתמשו ב-.get(). כל הרעיון הוא שסוגריים מרובעים קורסים כשהמפתח לא קיים, וזו בדיוק הקריסה שאתם הולכים לתפוס. ב-except הדפיסו <key> not exist.

prices = {'apple': 12, 'banana': 7, 'cherry': 25} print(prices) key = input("Which fruit? ") # try: print prices[key] <-- square brackets, not .get() # except KeyError: print(key, 'not exist')
מפתח שקיים
{'apple': 12, 'banana': 7, 'cherry': 25} Which fruit? banana 7 Goodbye
מפתח שלא קיים
{'apple': 12, 'banana': 7, 'cherry': 25} Which fruit? mango mango not exist Goodbye
יש כאן מלכודת. KeyError היא השגיאה היחידה שההודעה שלה שומרת על המרכאות:
except KeyError as e: print(e) # prints 'mango' - with the quotes!
לכן בנו את המשפט מתוך המשתנה key שלכם, ולא מתוך e, אחרת יודפס 'mango' not exist.
2 · לשנות ערך ב-tuple 🔒

קחו tuple, ונסו לשנות את האיבר באינדקס 0 ל-99. זה לא יעבוד — בדיוק על זה היה שיעור 19. תפסו את השגיאה במקום לתת לה להרוג את התוכנית, והדפיסו את ה-tuple אחר כך כדי להוכיח שהוא לא השתנה.

t = (1, 2, 3) # try: t[0] = 99 # except TypeError as e: print a message and print(e) print(t)
cannot change a tuple: 'tuple' object does not support item assignment (1, 2, 3) Goodbye
השגיאה שתופסים כאן היא TypeError, לא ValueError. הריצו פעם אחת בלי ה-try והטקסט האדום יגיד לכם איזו — זה ההרגל.
3 · למחוק משהו שלא נמצא ברשימה 🍊

הנה השורה. היא זורקת ValueError, כי אי אפשר למחוק משהו שמעולם לא היה שם:

fruits = ["apple", "banana"] fruits.remove("orange") # ValueError: list.remove(x): x not in list

עטפו ב-try / except ValueError, הדפיסו הודעה שאומרת איזה פרי חסר, והדפיסו את הרשימה אחר כך.

fruits = ["apple", "banana"] # try: fruits.remove("orange") # except ValueError as e: say orange is not in the list, print(e) print(fruits)
orange is not in the list: list.remove(x): x not in list ['apple', 'banana'] Goodbye
ואז תגרמו לזה לא לקרוס מלכתחילה. הוסיפו מתחת גם את הגרסה עם if "orange" in fruits:, כהערה או כבלוק שני. try / except הוא למה שלא יכולתם לבדוק מראש; בדיקת in פשוטה עדיפה כשכן יכולתם.
