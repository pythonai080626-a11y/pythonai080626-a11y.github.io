01

SQL, databases & engines

Slide 01
  • What is SQL?
    • Structured Query Language — the language we use to talk to a relational database
    • Like asking one very precise question: a single line of SQL replaces a whole Python loop
    • Four basic operations (CRUD): SELECT read · INSERT add · UPDATE change · DELETE remove
  • Why a database and not files / Excel?
    • Two people editing the same file at once overwrite each other — a database handles concurrent access
    • A database enforces rules (types, constraints) so your code doesn’t have to
    • Fast lookups and it keeps working with millions of rows
    • Files are still fine for small, single-user, throw-away data
  • What is an RDBMS? (Relational Database Management System)
    • Data lives in tables — rows are records, columns are fields
    • Tables are related to each other through keys, and read together with JOIN
    • Handled for you: concurrent access · ACID transactions · indexes · crash recovery · query optimisation
  • Famous SQL engines
    • PostgreSQL · MySQL / MariaDB · SQLite · SQL Server · Oracle
    • SQLite — serverless, the whole database is a single file; perfect for learning and the engine we use in this course
  • Installing SQLite & DB Browser for SQLitenot for exam
    • Download / install steps and the DB Browser walkthrough — setup only, nothing to memorise
02

Creating & changing tables

Slides 01 · 04
  • CREATE TABLE
    • CREATE TABLE name (column type constraints, …);
    • Every column = a name + a data type + optional constraints
  • DROP TABLE
    • DROP TABLE name; — deletes the table and all of its data
  • ALTER TABLE — change the structure of an existing table
    • ADD COLUMN — ALTER TABLE t ADD COLUMN col TYPE;
      • Existing rows get NULL in the new column
      • Fill it afterwards with UPDATE, or add it with a DEFAULT value
    • RENAME TO — rename the table: ALTER TABLE old RENAME TO new;
    • RENAME COLUMN a TO b — rename a column
    • DROP COLUMN col — remove a column
  • Inspect a table
    • PRAGMA table_info(table); — lists the columns, their types, NOT NULL, default and primary key
03

Data types

Slide 02
  • The 5 SQLite storage classes
    • NULL — no value / unknown
    • INTEGER — whole numbers
    • REAL — decimal numbers
    • TEXT — strings, written in single quotes 'like this'
    • BLOB — raw binary data, e.g. X'89504E47'
  • Type affinity
    • The declared column type is a preferred type, not a strict wall — SQLite converts values to it when it can
  • No real BOOLEAN / DATE / DATETIME types — they are stored as simpler types
    • BOOLEAN → stored as 0 (false) / 1 (true); TRUE and FALSE are accepted
    • DATE → TEXT in the format YYYY-MM-DD
    • DATETIME → TEXT in the format YYYY-MM-DD HH:MM:SS
04

Constraints & keys

Slide 02 · Lessons 2–3
  • Constraints — rules that protect your data; the database rejects any row that breaks them
    • NOT NULL — the column must always have a value
    • UNIQUE — no two rows may share the same value
    • CHECK (expression) — your own rule, e.g. CHECK (grade BETWEEN 0 AND 100)
    • DEFAULT value — filled in automatically when an INSERT gives no value
  • PRIMARY KEY — the unique identity of a row (unique + not null)
    • Single column: id INTEGER PRIMARY KEY
    • Composite primary key — two (or more) columns together form the key: PRIMARY KEY (student_id, course_id)
      • Each column may repeat on its own, but the pair must be unique
      • Typical use: a junction table for a many-to-many relationship
  • Auto increment
    • INTEGER PRIMARY KEY — if you omit the id, SQLite assigns the next number itself; may reuse ids of deleted rows
    • INTEGER PRIMARY KEY AUTOINCREMENT — never reuses an old id, always moves forward (slightly slower)
  • FOREIGN KEY — a column in the child table that points to the parent table’s key
    • FOREIGN KEY (col) REFERENCES parent(id)
    • Inserting a child whose parent doesn’t exist fails → create the parent row first
    • Deleting a parent that still has children fails (unless you chose a different ON DELETE action)
    • ON DELETE actions: CASCADE (delete the children too) · RESTRICT (block the delete) · SET NULL
    • PRAGMA foreign_keys = ON; — must be switched on (per connection), otherwise SQLite ignores foreign keys
05

INSERT · UPDATE · DELETE

Slide 01 · Lesson 2
  • INSERT — add rows
    • INSERT INTO t (col1, col2) VALUES (v1, v2); — name the columns, values in the same order
    • Without a column list you must give a value for every column, in table order
    • Several rows in one statement: VALUES (…), (…), (…)
  • UPDATE — change existing rows
    • UPDATE t SET col = value WHERE condition;
    • Several columns at once: SET a = 1, b = 'x'
    • The new value can be an expression: SET tax = amount * 0.07
    • CASE WHEN … THEN … ELSE … END inside SET gives different rows different values in one statement
  • DELETE — remove rows
    • DELETE FROM t WHERE condition; — the table itself stays
    • Without WHERE every row is deleted
  • Don’t forget WHERE
    • UPDATE or DELETE without WHERE touches every row
    • DELETE FROM t = empty the table · DROP TABLE t = remove the table completely
06

SELECT — filter & sort

Slide 03
  • The basics
    • SELECT * FROM t; — all columns
    • SELECT a, b FROM t; — only the columns you name
    • Calculated columns: SELECT price * 2 FROM t;
  • WHERE — keep only the rows that match
    • Comparisons: = · != / <> · < · > · <= · >=
    • Logic: AND · OR · NOT
    • Precedence: AND is evaluated before OR — use parentheses to control it
  • Pattern & range filters
    • LIKE — wildcards % (any number of characters) and _ (exactly one)
      • LIKE 'M%' starts with M · LIKE '%Pro' ends with Pro · LIKE '%an%' contains “an”
    • GLOB — Unix-style wildcards * (any characters) and ? (exactly one); case-sensitive
      • GLOB '????? *' = five characters, a space, then anything
    • BETWEEN a AND b — inclusive range (both ends count)
    • IN (v1, v2, …) — matches any value in the list
    • IS NULL / IS NOT NULL — the only way to test for a missing value (never = NULL)
  • Sorting & paging
    • ORDER BY col — ASC (default) or DESC
    • Several columns: ORDER BY a ASC, b DESC — the second only breaks ties of the first
    • LIMIT n — return only the first n rows
    • LIMIT n OFFSET m — skip m rows first → pagination
  • Aliases — AS
    • Rename a column in the output: SELECT price * 2 AS double_price
    • Short names for tables too (essential in JOINs); an alias can be used in ORDER BY
  • DISTINCT
    • Removes duplicates: SELECT DISTINCT country FROM t;
    • On several columns it removes duplicate combinations
  • Subquery — a query inside a query
    • e.g. the most expensive item: WHERE price = (SELECT MAX(price) FROM t)
  • Order the clauses are written in
    • SELECT → FROM → JOIN … ON → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT
07

Aggregations — group & summarize

Slide 04
  • Aggregate functions — many rows in, one value out
    • COUNT(*) — counts every row
    • COUNT(col) — counts only rows where col is not NULL
    • COUNT(DISTINCT col) — counts unique values
    • SUM · AVG · MIN · MAX
      • They skip NULLs — AVG divides only by the non-NULL rows (the hidden trap)
      • MIN / MAX also work on text and dates
  • GROUP BY — one result row per group
    • One column (GROUP BY region) or several (GROUP BY region, rep)
    • Every selected column must be in GROUP BY or inside an aggregate function
    • Sort by an aggregate using its alias: ORDER BY total DESC
  • HAVING vs WHERE
    • WHERE filters rows before grouping — it cannot use aggregates
    • HAVING filters groups after grouping — it can use aggregates, e.g. HAVING COUNT(*) > 2
    • You can use both in the same query
  • Clean-up & conditional logic
    • COALESCE(x, 0) — replace NULL with a fallback, e.g. COALESCE(SUM(amount), 0)
    • ROUND(x, 2) — round to 2 decimals, e.g. ROUND(AVG(amount), 2)
    • CASE WHEN … THEN … ELSE … END — if/else inside a query
    • Conditional counting: COUNT(CASE WHEN … THEN 1 END)
  • Common mistakes
    • Selecting a column that is not in GROUP BY and not aggregated
    • Putting an aggregate in WHERE (use HAVING)
08

JOINs — connecting tables

Slide 05 · Lessons 5–6
  • The idea
    • Data is split across tables and linked by keys; a JOIN puts the pieces back together
    • FROM a JOIN b ON a.fk = b.pk — the ON condition says how rows match
    • Use table aliases and table.column so column names are not ambiguous
  • INNER JOIN — only rows that match on both sides; everything else is dropped
  • LEFT JOIN — every row of the left table + matches from the right; no match → NULLs on the right
    • Find unmatched rows: LEFT JOIN … WHERE right.id IS NULL (e.g. departments with no employees)
  • RIGHT JOIN — the mirror image of LEFT JOIN; same result if you swap the table order
  • FULL OUTER JOIN — every row from both tables; NULLs on whichever side has no match
    • Only the unmatched rows from either side: WHERE a.id IS NULL OR b.id IS NULL
    • Replace the NULLs with COALESCE
  • CROSS JOIN — every combination of rows, no ON condition
    • rows(A) × rows(B) — the result grows fast
    • Use for combinations: sizes × colors, menus, rosters
  • Self-join — a table joined to itself using two aliases
    • e.g. employee ↔ their manager through manager_id
  • Joining 3+ tables
    • Chain several JOIN … ON … clauses; you can mix join types
    • Mind the order of the joins — especially with LEFT JOIN
  • JOIN + the rest of SQL
    • Combine with WHERE, GROUP BY, HAVING, ORDER BY — e.g. total spend per customer, employees per department
09

Relationships, normalization & design

Lessons 6–8
  • Relationship types
    • One-to-one (1:1) — e.g. citizen ↔ ID card
      • Shared primary key, or “1:1+”: its own primary key + a UNIQUE foreign key
    • One-to-many (1:N) — e.g. category → posts; the foreign key sits on the “many” side
    • Many-to-many (N:M) — e.g. students ↔ courses
      • Needs a junction table with two foreign keys and a composite primary key
  • Normalization — each fact stored once
    • 1NF — atomic values: one value per cell, no lists, no repeating columns like phone1, phone2
    • 2NF — 1NF + every non-key column depends on the whole key (no partial dependency; matters with composite keys)
    • 3NF — 2NF + no transitive dependency (a non-key column must not depend on another non-key column)
  • The design process
    • Identify entities → define attributes → map relationships → apply normal forms → draw the ERD before writing SQL
    • ERD: boxes = tables, lines = relationships, crow’s foot = “many”
    • Tools: dbdiagram.io (Ref: notation), draw.io, ERDPlus, QuickDBD, Lucidchart
  • Practice
    • Pizza-restaurant database; homework 18 — design and CREATE tables with primary and foreign keys

UNION & date queries

Lesson 8
  • Set operations — stack the results of two SELECTs
    • UNION — combine and remove duplicates
    • UNION ALL — combine and keep every row (including duplicates)
    • INTERSECT — only rows that appear in both results
    • EXCEPT — rows in the first result that are not in the second
    • Both queries need the same number of columns, with compatible types
  • Date queries with strftime(format, column)
    • Format codes: %Y year · %m month · %d day · %H hour · %M minutes · %S seconds · %w weekday (0 = Sunday)
    • %Y-%m-%d gives just the date
    • It always returns TEXT → compare with quotes (= '2026') or wrap it: CAST(strftime('%H', col) AS INTEGER)
    • Filter by year / month / day / hour, combine the conditions, and GROUP BY strftime('%m', col) to total per month
  • JULIANDAY() — days between two datesnot for exam
  • The end-of-day trick for BETWEEN on a date rangenot for exam
11

Running queries from Python

Slide 09 · Lesson 9
  • Python talks to SQLite with the built-in sqlite3 module
    • We wrapped it in a small db.py library and import it from main.py
    • Flow: connect → execute(sql, params) → read with fetchall() or save with commit()
  • The library functions
    • connect() — opens the connection; rows come back like dictionaries
    • run_query_select(sql, params) — for SELECT; returns a list of dicts
    • run_update_query(sql, params) — for INSERT / UPDATE / DELETE / CREATE; commits and returns lastrowid
  • CRUD from Python
    • All four operations — create, read, update, delete — go through those two functions
    • Changes are only saved to disk after commit()
  • SQL injection & ? placeholders
    • Never paste user input into the SQL string (f-strings / +) — an attacker can inject their own SQL
    • Write ? in the SQL and pass the values separately as a tuple; one ? per value, filled left-to-right
    • The value is always treated as data, never as SQL
  • Going further
    • Run a JOIN from Python — remember PRAGMA foreign_keys = ON when tables use foreign keys
    • Interactive programs: input() → INSERT, search by id, wrap the call in try / except
